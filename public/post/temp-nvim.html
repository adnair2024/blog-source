    Simplifying File Scaffolding with temp.nvim

    September 26, 2026

    A zero-dependency plugin for effortless template and frontmatter injection

    Every time I start a new file—whether it’s a new markdown blog post with Hugo frontmatter, a boilerplate Go script, or a React component—I find myself repeating the same tedious dance: copying frontmatter from another post, clearing out the old content, or searching for a boilerplate snippet.

    While full-featured snippet engines exist (like LuaSnip), they often feel like overkill when what you really want is full-buffer template scaffolding. Moreover, managing heavy dependencies across multiple machines can quickly complicate what should be a minimal, snappy Neovim setup.

    To solve this, I built temp.nvim: a lightweight, zero-dependency Neovim plugin designed to inject custom templates, boilerplate, and metadata directly into your buffers through an interactive prompt.

    The Problem: The Boilerplate Friction

    When developing across different languages or writing for static site generators, boilerplate is unavoidable:

    1. Static Site Generators (Hugo, Astro, Zola): You need precise YAML/TOML frontmatter with timestamps, slugs, and tags.
    2. Scripting (Bash, Python): You need standard shebangs, argument parsers, or if __name__ == "__main__": blocks.
    3. Configuration & Web Development: Boilerplate components, HTML skeletons, or license headers.

    Snippet plugins excel at short, inline expansions, but full-file templates often feel awkward inside them. You shouldn’t need a 500-line snippet definition just to load a base file format.

    I wanted something that:

    • Had zero external dependencies.
    • Utilized Neovim’s native UI elements (vim.ui.select and vim.ui.input).
    • Allowed quick creation, editing, and selection of templates.
    • Could dynamically inject contextual variables (like dates, file basenames, and titles).

    Designing temp.nvim

    The core philosophy of temp.nvim is minimalism and native integration. Neovim’s Lua API has matured tremendously, meaning we don’t need third-party UI libraries to build an interactive, polished experience.

    1. Native UI Integration

    Instead of bundling custom floating windows or demanding telescope.nvim as a strict dependency, temp.nvim relies on vim.ui.select. If you use telescope.nvim, fzf-lua, or dressing.nvim, temp.nvim automatically inherits your styled selector. If you run vanilla Neovim, it falls back cleanly to the built-in command-line menu.

    -- Simplified logic behind template selection
vim.ui.select(available_templates, {
    prompt = "Select Template to Inject:",
    format_item = function(item)
        return item.name .. " (" .. item.filetype .. ")"
    end,
}, function(choice)
    if choice then
        inject_template(choice)
    end
end)

    2. Dynamic Placeholders

    Static templates only solve half the problem. Blog posts need current timestamps; code files need current filenames and module names. temp.nvim processes simple token replacements before inserting the template into the buffer:

    • {{date}}: Formatted ISO 8601 or custom date string.
    • {{filename}}: Base name of the current buffer.
    • {{title}}: Clean, title-cased representation of the file name.
    • {{author}}: User-configured author name.

    3. Buffer-Safe Injection

    A common frustration with template inserters is accidentally overwriting work in an existing buffer. temp.nvim checks if a buffer is empty or if the user explicitly triggered an append/prepend action, ensuring you never accidentally overwrite existing code.

    Installation & Configuration

    Installing temp.nvim with lazy.nvim is straightforward:

    {
    "adnair2024/temp.nvim",
    cmd = { "TempInject", "TempNew" },
    keys = {
        { "<leader>ti", "<cmd>TempInject<cr>", desc = "Inject Template" },
    },
    opts = {
        templates_dir = vim.fn.stdpath("config") .. "/templates",
        variables = {
            author = "Ashwin Nair",
        },
    },
}

    Why Build Minimal Tools?

    Building temp.nvim reinforced something I appreciate about the Neovim ecosystem: the best plugins are often small, focused utilities that do one job well without imposing a massive abstraction layer.

    By keeping the plugin dependency-free and adhering strictly to the vim.api and vim.ui interfaces:

    • Startup time impact is essentially 0 ms.
    • It will continue to work across Neovim versions without breaking changes from third-party libraries.
    • The codebase is easy to read, tweak, and contribute to.

    If you want to streamline your workflow and stop copying boilerplate by hand, check out temp.nvim on GitHub!
